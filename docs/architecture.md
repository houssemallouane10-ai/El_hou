# Architecture notes

خدمتي is a modular monolith: one Node.js process serves the JSON API, the app shell and the
static PWA. One SQLite database (WAL mode) is the system of record.

## Domains and ownership

| Domain | Owns (authoritative writes) | Public entry | Depends on |
| --- | --- | --- | --- |
| `accounts` | `users`, `sessions` — registration (with terms acceptance), login, profiles and their wilaya/commune, worker directory, alert settings, owners and admin flags | `server/domains/accounts/index.js` | — |
| `notifications` | `notifications` — in-app notices and job-alert fan-out | `server/domains/notifications/index.js` | — |
| `jobs` | `jobs` — offers and their lifecycle (active → closed / expired, renew, moderation hide) | `server/domains/jobs/index.js` | accounts, notifications |
| `applications` | `applications` — apply, withdraw, employer decisions | `server/domains/applications/index.js` | jobs, accounts, notifications |
| `bookmarks` | `saved_jobs`, `saved_workers` | `server/domains/bookmarks/index.js` | jobs, accounts |
| `messaging` | `conversations`, `messages`, `blocks` — one conversation per pair of people; blocking | `server/domains/messaging/index.js` | accounts, jobs |
| `moderation` | `reports` — reports and the admin console | `server/domains/moderation/index.js` | accounts, jobs, applications, messaging, notifications |

Rules:

- Each table has exactly one writing domain. Other domains call its service.
- Repositories may join another domain's table **read-only** for display and visibility
  (poster names on job cards, applicant details for the employer, banned-account filtering).
- Routes are thin: parse ids, call one service, shape the HTTP response. Business failures are
  `DomainError`s (`server/shared/errors.js`); `server/shared/http/errors.js` maps them to statuses.
- Composition happens in `server/services.js` (services) and `server/api/router.js` (routes,
  rate limits, session cookie, composite endpoints `/api/session`, `/api/me/summary`, `/api/meta`).

Shared, browser-safe contracts live in `shared/` (catalog of categories and job types, the
generated wilayas and communes in `geo.js`, field limits, Algerian phone rules, the page-text
format) and are imported by both the server and the browser.

## Places

- `shared/geo.js` lists Algeria's 69 wilayas and 1,541 communes (Law 26-06 of 4 April 2026). It is
  generated by `scripts/build-geo.js` from two MIT datasets plus hand-checked fixes. **Commune ids
  are stored in the database and must never be renumbered.**
- Rows store `wilaya_code` and `commune_id`. A job offer must name a commune; a profile needs a
  wilaya and may name a commune. `server/shared/places.js#resolvePlace` derives the wilaya from the
  commune and rejects pairs that disagree, so the two columns can never contradict each other.
- Search text includes place names in Arabic and French, so "تبسة" and "Tébessa" both match.
- The browsing region (a wilaya, or the whole country) is a per-device preference in the browser
  (`public/js/app/region.js`), defaulting to the account's wilaya; lists accept `?wilaya=` and
  `?commune=` so shared links keep working.
- Migration 2 maps version-1 slugs (the communes of Tébessa) to national ids; maintenance re-indexes
  the affected rows' search text on start-up.

## Owners, moderators and store requirements

- Owners are the phones in `ADMIN_PHONES`: always admins, never demotable from the app, and the only
  accounts that appoint or remove moderators (`accounts.adminSetAdmin`).
- Google Play's user-generated content rules are met in the domains, not just the UI: explicit terms
  acceptance at registration, reports on offers and users, and blocks that stop messages both ways
  (`messaging`), plus in-app and web account deletion.
- `/privacy`, `/terms`, `/about`, `/safety` and `/account-deletion` are rendered on the server from
  the Arabic locale, so reviewers and crawlers can read them without JavaScript.
- `/.well-known/assetlinks.json` is built from `ANDROID_PACKAGE_NAME` and
  `ANDROID_SHA256_FINGERPRINTS`; malformed fingerprints stop the server at start-up.

## Key decisions

| Decision | Why | Revisit when |
| --- | --- | --- |
| SQLite + better-sqlite3 | Zero-ops, fast, one file to back up; suits a single server (wilaya and commune filters are indexed); not load-tested at national traffic yet | Several app instances are needed (move to Postgres) |
| No front-end build step (native ES modules) | Nothing to compile on deploy; easy to edit | Bundle size or module count becomes a measured problem |
| Derived job state (`jobState`) | Expiry needs no cron job and can never go stale | — |
| Notifications store type + data, not text | The browser renders them in Arabic or French | — |
| In-process rate limits and view de-duplication | Single instance; no extra infrastructure | Scaling out (use a shared store) |
| Server-rendered meta in the shell | WhatsApp/Facebook previews for shared job links | — |
| Service worker version = hash of assets | Every deploy that changes a file prompts an update | — |

## Known limits

- Phone numbers are not verified by SMS; moderators reset forgotten passwords.
- Notifications reach users while the app is open (polling every 30 s); there is no push yet.
- Rate limits and view de-duplication are per process.
- Place names follow the 2026 division; renamed communes are fixed in `scripts/build-geo.js` and the
  module regenerated (ids stay the same).
- A block stops private messages only: public offers and listed profiles stay visible to everyone.
